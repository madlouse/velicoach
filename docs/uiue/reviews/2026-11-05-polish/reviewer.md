## 0. 结论

- **玻璃放的位置和设计系统那张表一致**：首页导航、订阅条、暂停按钮和看清的导航都是实色面；站稳和文章页的吸顶导航、本站操作条、播放条、动手导航和「然后动手」圆用了 `lg`。
- **只有「然后动手」圆不对**。它背后其实没有动效，四帧里粒子都没经过圆的后面；苔绿底色的浓度是 74%–90%，而做法给的范围是 10%–30%。结果它看起来是一块被接缝劈成两种绿的实色圆片，不像清透的玻璃。另外，真实画板上的圆没有悬停和按下的样式，`.orb` 类只出现在控件状态画板上。
- **滚动类的玻璃还没有证据**：「滚过首屏」那张截图里，玻璃背后是空白的纸色。浅色下本站操作条偏奶白，`(254,254,246)`，页面是 `(244,242,236)`；深色下全宽的条左端有一团内光，看起来像灰斑。2px 的模糊压在正文上读起来怎样，没人看过。
- **动效截图没有挂透镜**：`capture.py` 只调用了 `startGL()`，没跑 `componentDidMount()`，所以 `attachLens` 一次也没执行。四帧都是不带透镜的样子。
- 打磨方面，按「影响 × 改动大小」排出 8 处（§3）。最值得先做的三处：圆改成实色主按钮；研究卡把已有的 `metric` 数字显示出来；吸顶的两层条并成一层。

### 2.2 问题

**G1 · 「然后动手」圆：声明的背景和实际不符，材质成了劈开的实色圆片 · P2**
- 画板和状态：首页（静态和四帧）、手机 390/320、平板、折叠屏，浅色和深色。
- 元素：`Main.dc.html:147`、`Mobile.dc.html:93`、`Tablet.dc.html:87`、`Fold.dc.html:88`，类是 `lg lg-on-dark lg-moss`，带 `data-backdrop="motion"`。
- 违反：设计系统「玻璃只给背后会变的那一层；背后是平涂底色时用实色面」；V5「玻璃要看得出背后的内容，看不出的就改成实色面」；`liquid-glass.md` §1 浅色模式压在暗处时的底色浓度是 10%–30%，而 `vc.css:367` 是 `0.74 + 0.16 × density`。
- 证据：
  - 四帧里粒子的下沿，叶在 y≈400，网在 y≈450；圆从 y≈616 开始（按 1440×900 换算）。圆背后始终是一半纸、一半墨，两块都是平涂。
  - 圆一直跟着接缝移动（`left: {{seamLeft}}`），所以背后的两色比例永远不变，背后其实不会变。
  - 裁图 `rvA/circle.png`：左半 `(73,88,78)`，右半 `(35,51,40)`，中间一条硬边。手机上接缝横穿「然后动手」和「开发日志」两行之间（`rvA/morb.png`），像印刷错位。
  - `data-backdrop="motion"` 让 `verify_canvas.py` 跳过了「玻璃压在平涂底色上」这一项（`verify_canvas.py:339`），所以规则检查全过，并不说明它是对的。
- 期望：材质和背后一致。这个圆是第三站唯一的入口，本质上是一枚主按钮，按设计系统「主按钮不用玻璃，对比度最要紧」处理。
- 实际：一块 82% 浓度的苔绿，透出来的只有接缝。看不出模糊、透镜和色散（浓度这么高，透镜弯过来的背景只剩 10%–26%）。

**G2 · 真实画板上的「然后动手」圆没有悬停和按下样式 · P1（底线 U9）**
- 元素：`.orb:hover`、`.orb:active` 写在 `vc.css:206–207`，但四块真实画板上的圆都没有 `orb` 类，也没有 `lg-hoverable`。只有 `Controls.dc.html:67` 的样品有。
- 违反：U9「每个控件都有悬停、按下、焦点三种样式」；设计系统「按钮的状态」。另外，`.orb` 现有的写法是叠一层灰（`--vc-state-hover`，灰 12%），这和 `liquid-glass.md` §1「不用灰色蒙一层」、§2「悬停把底色提亮约 14%」冲突。
- 证据：`grep orb project/Main.dc.html` 没有结果；`vc.css` 里能落到这个元素上的 `:hover` 只有 `.lg.lg-hoverable:hover`。
- 期望：首页、手机、平板、折叠屏上的圆都有悬停（变亮）、按下（压暗，内容下移 1px）和焦点外圈，每一档都过 4.5:1。
- 实际：鼠标放上去、按下去都没有任何反馈。上一轮 A1 的对比度问题，是靠把状态整个去掉才「解决」的。

**G3 · 滚动类玻璃（站稳、文章、动手的吸顶导航和操作条）没有「背后有正文」的证据，2px 模糊在正文上有风险 · P2**
- 元素：`.gnav.lg`、`.localtop.lg`、`Article .topnav.lg`；`--lg-blur: 2px`（`vc.css:265`）。
- 违反：`liquid-glass.md` §6「在产品允许的最忙、最暗的背景上……检查文字对比度」；V5「按最差的那块底算对比度」。
- 证据：`Body-scrolled-滚过首屏-light/dark.png` 顶部 0–80px，背后只有空白的纸色或墨色，没有一行正文。四帧动效截图只覆盖首页。
- 期望：至少各有一张截图，让正文的一行黑字正好从「为什么是肌肉」这类链接后面滚过，量链接和背后文字笔画之间的对比度。
- 实际：没有截图。2px 模糊几乎不糊字，背后的 16px 正文会和导航文字叠在一起读。苹果的导航栏在滚动内容上用的是厚材质，加上边缘的渐隐（scroll edge effect），不是透明的薄玻璃。这一点是推断，需要截图确认，所以记 P2，不记 P1。

**G4 · 全宽通栏套用了小表面的玻璃配方：浅色奶白，深色灰斑 · P2**
- 元素：`.localtop.lg`（`Body.dc.html:112`），宽 1440px、高 68px。
- 违反：V5「不用不透明的灰块」；`liquid-glass.md` §1「颜色来自背后……不发白」。
- 证据：
  - `rvA/bodytop-light.png`：条是 `(254,254,246)`，页面是 `(244,242,236)`。白色底色、`saturate(180%)` 和 `brightness(1.06)` 叠在暖纸色上，把纸色推成了偏黄的奶白。
  - `rvA/bodytop-dark.png`：左端 0–300px 有一团径向高光，来自 `.lg::before`。这团高光是按圆角小表面设计的，铺到 1440px 宽的条上，就成了一块不均匀的灰斑。
- 期望：通栏玻璃的颜色和页面底色同一色相，只靠模糊和细边缘区分；没有局部的光斑。
- 实际：浅色看起来是一条奶白色的带子；深色看起来是左边亮、右边暗的灰条。

**G5 · 动效截图没有挂透镜，评审拿不到「边缘像厚玻璃」的证据 · P2（流程）**
- 元素：`shots-r9/motion/capture.py` 的 `HARNESS` 只调用了 `c.startGL()`；`attachLens` 写在 `componentDidMount()` 里（`Main.dc.html:474–476`），从没执行过。
- 违反：`liquid-glass.md` §7.4「在最忙、最暗的背景上截图量对比度」；标杆卡 P4 的证据要求。
- 期望：四帧在 `startGL()` 之前先执行 `document.querySelectorAll('[data-lens]').forEach(el => LiquidGlass.attachLens(el))`，等 `img.decode()` 完成后再截图。
- 实际：派活时说动效截图「真实 WebGL 加透镜」，其实没有透镜。G1 里说看不出透镜，一半原因在这里，另一半是浓度太高。

### 2.4 退路

- 降低透明度：`.lg` 换成 `--lg-solid`（纸色面），`.lg-on-dark` 换成墨色面，`.lg-moss` 换成 `--vc-moss-hero`，同时关掉内光，`vc.css:342–345`、`:368`。对。
- 强制颜色：用 `Canvas`/`CanvasText`，去掉内光和混合模式，`vc.css:347–350`。对。
- 不支持背景滤镜：`:353–354` 换成实色。对。
- 透镜只在 Chromium 上挂，`will-change`、小于 32px 和降低透明度的情况都跳过（`liquid-glass.js:110–117`）。对。

## 3. 打磨空间：最影响观感和体验的 8 处

排序按「影响 × 改动大小」：影响高、改动小的排在前面。参照：apple.com（产品页的本地导航、实色主按钮）、linear.app（浮层不挤动版面、碰到边界就翻转）、stripe.com（数字先行的卡片、栅格对齐）、Distill（侧注和读者路径）。

对照两位标杆，差距最大的两处：

- **apple.com**：主操作永远是实色的，玻璃只放在导航和浮在内容上的控件上；滚动时只留一条本地导航。这里第 1 条和第 3 条正好是这两点。
- **Stripe / Our World in Data**：数字卡先给数字，再给一句话，再给出处。研究卡的出处、样本量和证据可信度都做到了，只差把数字放到最前面（第 2 条）。这是最便宜的一处提升。

## 5. 设计技能缺了什么，才会第一次就犯

| 问题 | 技能里缺的做法 | 建议写进哪里 |
|---|---|---|
| G1 圆的背景声明和实际不符 | `data-backdrop` 是开发者自己写的声明，检查只看「有没有写」，不看动效或视频的区域和这个表面有没有重叠。技能里也没有「表面跟着接缝走时，背后的比例不变，等于平涂」这条判断 | `liquid-glass.md` §0：声明 `motion` 时要给出动效的区域，`verify_canvas.py` 用四帧截图算一下动效像素和表面的重叠，重叠为 0 就照样报「平涂」 |
| G1 苔绿浓度 74%–90% | 做法只给了白、黑两种底色的浓度范围，没有说品牌色玻璃怎么定浓度，也没有说「浓度超过约 50% 就不再是玻璃，改实色」 | `liquid-glass.md` §1 加一行：带品牌色的玻璃浓度上限，超过上限就改成实色面；`velicoach-layout` §8 加上 `lg-moss` 的上限 |
| G2 真实画板上缺状态 | 控件状态画板上的样品和真实画板用的类可以不一样，没有检查要求「每个可点元素在真实画板上都匹配到 `:hover`、`:active` 规则」 | `verify_canvas.py` 加一项「可点元素没有悬停或按下样式」，按计算样式比较默认、`:hover`、`:active` 三种状态，或者检查有没有 `is-hover`、`is-press` 的变体类 |
| G2 `.orb` 叠灰色 | `buttons-and-glass.md` 写了「按下压暗」，没写「玻璃的悬停用提亮底色，不叠状态灰」，和 `liquid-glass.md` §1 不一致 | `velicoach-layout/references/buttons-and-glass.md` 引用 `liquid-glass.md` §1–2 的状态做法，删掉玻璃上的 `vc-state-*` |
| G3 滚动玻璃没有证据 | 交付只要求「在最忙的背景上截图」，没说滚动类玻璃该怎么截；画板的「滚过首屏」状态让人以为已经覆盖了 | `liquid-glass.md` §7 和 `velicoach-layout` 的交付检查：`data-backdrop="scroll"` 的表面必须有一张「正文的一行字从导航文字后面滚过」的截图，并量对比度 |
| G3 2px 模糊用于滚动正文 | 做法只给了一档 `blur(2px)`，适合压在图片、动效上的小控件，没有按背后是图像还是文字分档 | `liquid-glass.md` §1：背后是文字（`scroll`）时用厚一档，模糊 16–24px，加边缘渐隐 |
| G4 通栏用了小表面的配方 | 内光和白色底色是按圆角小表面写的，没有说通栏、全宽工具栏怎么做 | `liquid-glass.md` §1：宽度超过约 600px 或贴边的表面不画径向高光，底色取背后主色，不用白色 |
| G5 动效截图不带透镜 | 动效截图的做法没有要求执行页面挂载时的代码（透镜、墨色自适应） | `design-bar` 截图脚本的说明：截动效时先跑 `componentDidMount`，或者明确执行 `attachLens`，等解码完成再截 |
| #2 数据有了却没画 | 没有检查「内容模型里的字段在画板上有没有出现」 | `design-bar` 的覆盖检查（`coverage.py`）加上「数据字段 → 画板」的对照 |
| #3 两层吸顶条 | 技能规定了全局导航和本站操作条各自的样子，没规定两者同时吸顶时怎么办 | `velicoach-layout` §7：同一时刻只吸一条；本站操作条吸顶时全局导航收起 |
| #4 展开挤动版面 | 「原地展开」只规定了位置和时长，没要求「展开不移动触发元素上方的内容」，也没写空间不够时怎么翻转 | `velicoach-layout` 原地展开一节加两条：用覆盖层不挤版面；空间不够时翻转，不压主标题 |
| #5 收起的一侧节奏、订阅条不跟接缝 | 倾斜规则只写了 62/38 和「收起说明文字」，没写收起之后元素怎么重排，也没列出哪些元素要跟着接缝走 | `velicoach-layout` 三种版式一节：列出跟着接缝走的元素（导航、圆、订阅条）；收起的一侧整列贴底排 |
| #6 首屏和正文的左边缘不齐 | V6 只要求两半「彼此」对齐，没要求首屏和下面的正文共用栅格线 | V6 或设计系统「版式」加一条：首屏的文字起点和 `content-max` 的边缘对齐 |
| #7 平板上的手动断行 | 孤字、词中断行的检查不认识「AI 后面断行」这种中英混排的断法 | `verify_canvas.py` 词中断行：西文词后面紧接着中文、又被拆到两行时也报 |

## 6. 规则缺口（不算问题，交主会话决定要不要补规则）

- 背后声明的真实性：V5 和 `data-backdrop` 都没有规定「声明的背景必须真的从表面后面经过」。
- 叠在一起的玻璃：HIG 不建议玻璃叠玻璃，`quality-terms` 没有这一条（对应 §3 #3）。
- 浮层展开时不移动触发元素和上方的内容（对应 #4），现在只是观感，还没有规则。
- 签名动效时的整体构图：倾斜时哪些元素跟着接缝走，没有规则（#5）。
- 数字卡的阅读顺序（数字 → 结论 → 出处）是 Stripe 和 OWID 的惯例，`quality-terms` 的 T 系列没有写（#2）。
