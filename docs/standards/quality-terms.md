# 质量词：把形容词和动词变成可检查的规则

> 建立：2026-11-04 · 产品负责人：「所有的点，包括需求点、原因和逻辑，都要做系统性的、批判性对抗的评审，用金字塔原理，确保不重不漏。不清晰的标准也必须有清晰的规则。比如『体验友好』：不是网上找找就行，要看有没有对标的产品，再基于对标产品的特征来定义。你说体验友好，就必须有几个特性、几条规则能把它评审清楚、定义清楚，不管是名词还是动词。」
> 以谁为准：质量词的意思以本页为准；本页和 PRD、设计系统冲突时以它们为准，并回来改本页。
> 依据：三组对标研究（2026-11-04 查询，出处写在每条规则后面）；PRD；设计系统；`design-bar` 的 `references/rubric.md`。查不到的写「未查到」；自己定的数写「自定」和理由，观察者两周后按实际数据复核。
> 版本：第 2 版（2026-11-04），按一次对抗评审的 8 类发现重写：维度之间的分界写明、看清的规则并回各维度、补上漏掉的要求、每条规则写适用范围和谁来查、检查脚本核对规则编号。

## 1. 结论

**「体验友好」由好用、好懂、好看、可信、舒适五个维度组成，共 51 条规则（§2、§4）。一个质量词只有在能判对错时才能用：它要有对标、从对标上观察到的特征、由特征推出的规则、适用范围、检查方法和门槛。** 验收里出现没定义的质量词，或者「适当」「尽量」这类判不了对错的虚词，检查不通过（`npm run check:vague`）。

## 2. 总树

### 2.1 五个维度和分界

按用户心里的五个问题分，一个问题对应一个维度：

| 维度 | 用户的问题 | 管什么 | 收进来的词 | 规则 |
|---|---|---|---|---|
| 好用 | 我能不能快、顺地做成想做的事？ | 路径和操作：找得到、步数、反馈、速度、出错和失败、键盘、换设备姿态不打断 | 好用、易用、易上手、简单、一眼、直观、顺手、流畅 | U1–U13 |
| 好懂 | 我看不看得懂？ | 文字和信息：句子、段落、术语、按钮文字、不用读就会用、图表、结构、两种语言 | 易懂、易理解、通俗、白话、清楚、清晰 | C1–C9 |
| 好看 | 它看起来是不是用心做的、有自己的样子？ | 视觉秩序和身份：字体、颜色、版式、材质、动效的含义、排版细节、模板味 | 好看、美观、高级感、高级、有品味、品味、极简、简洁、克制、精致、质感、赏心悦目、干净、苹果设计语言 | V1–V10 |
| 可信 | 我信不信它说的？ | 出处、日期、更正、判断、健康内容、不操纵、只放正式版 | 专业、可信、有深度、有分量、值得读 | T1–T10 |
| 舒适 | 用着累不累、会不会被打扰？ | 感官和身体的负担：看得清、点得准、能缩放、不晕、不被打扰、读不累、媒体有替代、不被折痕挡住 | 舒服、舒适、不打扰、轻松、好读 | A1–A8 |

分界容易混的地方，按这几条判：

- 键盘能不能做完、焦点在哪里：属于**好用**（路径）。点按区域多大、对比度够不够：属于**舒适**（身体）。
- 动效有没有含义、是不是唯一的签名：属于**好看**。动效会不会让人晕、能不能停：属于**舒适**。
- 字号、行宽、行高：属于**舒适**（读不累）。中西文间距、标点、标题换行：属于**好看**（排版细节）。句子和段落多长：属于**好懂**。
- 文章怎么组织（问题 → 方案 → 总结、侧注、图表）：属于**好懂**。元信息里的日期和更新属于**可信**，其余放什么、不放什么属于**好看**（克制）。

### 2.2 组合词

- **体验友好**：五个维度里，适用于这一页的规则全部通过。
- **专业又通俗易懂**：可信（T）和好懂（C）同时通过。
- **拿奖级**：体验友好，再按 Awwwards 的权重评分：设计 40%、可用性 30%、创意 20%、内容 10%（[Awwwards 评审说明](https://www.awwwards.com/about-evaluation/)）。两份独立设计评审各打 1–10 分，加权平均都 ≥ 7.0、单项都 ≥ 6.5。6.5 是 Awwwards 荣誉提名的分数线（[FAQ](https://awwwards.com/faqs)）；7.0 是自定，留出余量；Awwwards 没有公布每日最佳的分数线（未查到）。四项对应标杆卡的原则：设计 → P2、P5；可用性 → P1；创意 → P4；内容 → P3（`docs/uiue/bar-sheet.md`）。
- **极致**：拿奖级。
- 不进检查的词：「一致」「统一」「完整」带了参照物就能判（「和术语表一致」「清单完整：逐条有着落」），所以不列进 §8；没有参照物时同样不能用。

## 3. 怎么定义一个词

1. **先问用户因为它能做成什么**：每个质量词都回到 PRD 的目标，说不出对用户的作用，这个词就不该出现。
2. **选对标**，四条都满足：做的是同一类任务或面向同一类读者；有公认的证据（获奖、被同行引用、行业规范）；页面公开、能直接观察；至少两个来源。只有一个来源的规则标「单一来源」，观察者优先补第二个。
3. **观察对标**：只记能观察到的特征（数得出、量得出、截得到图），每条附网址和查询日期。查不到的写「未查到」。
4. **推规则**：几个对标共有的特征才变成规则，一家的个例不算共性。每条规则写清适用范围、谁来查、门槛。
5. **对抗**：找反例，即满足了全部规则、用户仍然觉得不好的情况。找到就说明规则不完整，补一条。
6. **不重不漏**：一个词只归一个维度；同义词并进同一个条目；同一条规则只写在一个地方，别处引用编号。

### 4.3 好看（V）

### 4.6 用这些规则对照现有设计，发现的冲突

对抗评审的结果，交给关口三 a（#14）处理：

1. **英文正文太宽、行距太大**：正文版心 640px、16px 时，英文每行约 80–90 个字符，超过 A6 的 75；英文行高 1.7 超过 1.45 倍。中文 640px ÷ 16px = 40 字，正好在上限。英文版要单独定字号、版心或行高。**已定（第 2 轮）**：英文正文 18px、行高 1.45、版心 612px（`text-max-en`），每行约 68 个字符；中文正文 17px、行高 1.8、版心 640px，每行约 37 字（设计系统「字体」）。
2. **首页「叶与网」一直在动**：不悬停时 10 秒一次呼吸，A4 要求能暂停。现在滚出视野会停，还缺一个暂停的方式。**已改（第 1 轮）**：首屏右上角加暂停按钮。
3. **语言切换的点按高度 38px**，小于 A2 的 44px（手机、平板画板）。**已改（第 1 轮）**：分段控件每项 44px。
4. **站稳、动手两块画板写死了 145 处颜色**，违反 V6。**已改（第 1 轮）**：两块画板重做，只用 token。

这一版改规则时和 PRD、设计系统对齐的地方（规则让步，不算设计的问题）：C4 放宽到 8 个字（「进入今天的训练」是 7 个字）；V1 改成设计系统的「字体三种」，首页看清一侧也用衬线；V2 改成设计系统的「三站，三种底色」；V3 按区域算，不按整个首屏；V7 区分首页和分站；V8 加上作者；A6 的英文行长统一为 `velicoach-layout` 的 60–75。

## 5. 动词：每个动作写清产出和完成的标准

| 动词 | 产出 | 什么时候算做完 |
|---|---|---|
| 打磨 | 按 `design-bar` 第 5 步一轮一轮改：只读检查 → 独立评审 → 修前 3 项 | 标杆卡的停止条件（`docs/uiue/bar-sheet.md` §7） |
| 优化、提升 | 写明哪个指标、从多少到多少、怎么量 | 量到了目标值；没写指标的「优化」不能进票 |
| 完善、补齐 | 列出缺的条目清单 | 清单逐条有着落：补上了，或写明为什么不补 |
| 梳理、汇总 | 一份文档或一张表，结构是金字塔：结论、分组、依据 | 每条依据追到原话、PRD 或出处；分组不重不漏 |
| 重写 | 按目标读者重新组织和措辞，不逐句对应 | 英文版：C1、C2、C7 通过，读者不看中文版也能读懂 |
| 评审 | 一条结论评论：通过或要改，阻塞项带位置和改法 | 实际跑过检查；每条发现有可信度分，低于 80 不报 |
| 对抗评审 | 由没看过制作过程的新 Agent 做；按金字塔自上而下：结论能不能被下层支撑，同层是否不重不漏，每条理由能不能追到来源，有没有反例 | 发现逐条有去向；设计的两份评审用不同模型、互相看不到 |
| 走查 | 按主线一步一步操作真实页面或画板，逐条对照规则 | 每条问题写明位置、违反的规则编号、严重度、截图 |
| 验证、核对 | 打开出处或实际运行，找到原句或看到结果 | 原句摘录、命令和输出写在证据里 |
| 复核、抽查 | 按规定的比例重做一遍别人的检查（观察者：阶段 1 每个 PR，之后 3 个抽 1 个） | 结果和原结论一致，或写明不一致的地方 |
| 校准 | 按 `velicoach-content` 的校准清单逐项核对已上线内容 | 每项有结论：仍然成立、已更新、已下线 |
| 同步 | 把一处的改动带到另一处（在线文档到快照、仓库技能到账号副本、Veli 版本号） | 两处内容一致，同步的版本或日期写明 |
| 收录 | 按 `article-pipeline` 把一篇文章放进看清 | 那份技能的最后一步做完 |
| 定稿 | 产品负责人合并带 `owner:merge` 的内容 PR | PR 已合并 |
| 举一反三 | 找出这条意见背后的原则，列出所有同类位置 | 同类位置都改了；原则写回技能、设计系统、规范或术语表；`trace.md` 记一笔 |
| 沉淀 | 规则写进对应文档，能机械检查的写成检查 | 同一类意见第二次出现时，已经有对应的规则或检查 |
| 对齐 | 写明和谁对齐、以哪份文档为准、改了哪一方 | 两份文档不再冲突；改动记在 `trace.md` 或 `decisions.md` |

## 7. 怎么用

- 验收里用到 §8 的质量词：写上它所在维度的规则编号「quality-terms <规则编号>」（例如「首页好看：首屏每个区域只放标题、一句说明和操作，quality-terms V3」），或者直接把规则写进验收。编号必须真实存在，而且要和这个词属于同一个维度（「好看」要引 V 开头的规则），脚本会核对。
- 「体验友好」「拿奖」「极致」这类组合词，写「quality-terms §2.2」，或者拆成具体规则。
- 加了引号只对虚词有效（表示在提到这个词）；质量词加了引号照样要有定义。
- 检查范围：勾选项；标题含「验收」「完成标准」「出口」「退出条件」等字样的小节下的列表；表格里表头含「验收」「出口」「交付物」「怎么查」「门槛」「完成标准」等字样的列。说明性的正文不查。
- 新的质量词：先按 §3 定义，加进 §2.1 的词表和 §8，再用。
