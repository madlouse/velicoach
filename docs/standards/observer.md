# 观察者：主站流水线的质量保障

> 建立：2026-11-04 · 复用 Veli `docs/standards/observer.md`（版本见 `pipeline.md` §9）的全部机制：目标函数、两个方向、规则账本、归因顺序、权限、紧急刹车。本页只写主站多出来的两件事：看两条车道，看设计和内容的质量；后者复用 `design-bar` 的独立评审和只读验证者的做法。
> 冲突时：本页 §4（权限）只能由产品负责人改，其余以 Veli 原文为准。

## 1. 目标

**观察者是机制的微调回路：在质量不降的前提下，让返工和等待最少。** 两个方向都看：Agent 没按机制做，就收紧；机制在拖慢进度或逼出低质量的结果，就提出简化。每条规则算两笔账：拦下过什么，又花了多少等待和返工（Veli `observer.md` §1.1）。

票推进器做事，冷评审管单个 PR，观察者从外面管整条流水线。

## 2. 每次看什么

照 Veli `observer.md` §2–§5：先看组织和协作（`pipeline.md` §3 的角色表：交接物有没有留下、接手方有没有读、哪一段没人负责），再看过程合规（每次运行的运行锁、领票、证据、评审、合并、交接）、证据能不能在干净检出上重跑、冷评审的漏检。主站另外看：

| 方面 | 看什么 | 到位的标准 |
|---|---|---|
| 两条车道 | 站点和内容各自的吞吐、周期、返工；有没有越过 `pipeline.md` §4.1 的路径边界；跨车道的依赖是不是用「被谁卡住」连起来了 | 越界 0 次；跨车道的依赖都有链接 |
| 设计质量 | 合并的界面 PR 抽查：自己在预览上按 `pipeline.md` §7 的参数跑 `check_page.py`，对照画板和 `velicoach-layout` 再做一次独立评审，记评审漏检 | 只读检查结论 `done`；漏检记进指标 |
| 内容质量 | 合并的内容 PR 抽查：随机打开 3 处出处核对原句；授权状态；术语；英文是不是按英语读者重写 | 出处可复现 100%；授权不明的只做讲解和摘要 |
| 需求覆盖 | PRD v1 的每个功能：有票、有画板状态、有验收；还没画的写明理由 | 当前里程碑 100% 有验收 |
| 质量词 | 验收和评审结论里的质量词是不是都链到了 `quality-terms.md`；评审写的「规则缺口」有没有补进规则；「自定」的数两周后按数据复核 | `check:vague` 通过；规则缺口都有去向 |
| 人的注意力 | 等你决定的事、周一选题和周五定稿有没有按时被处理，卡在人身上的等待有多长 | 等你决定 ≤ 3 条 |

## 3. 设计和内容的评审，怎样才可信（复用 `design-bar`）

观察者检查评审本身是不是按这几条做的，不是就按 Veli `observer.md` §6 归因：

1. **独立评审，不自评**：评审者没看过制作过程，只拿到截图、需求、设计系统、标杆和上一轮的问题清单，并逐条核对上一轮的问题是否真的解决。制作者自己打的分不算通过。
2. **只读验证者只给结论**：`verify_canvas.py`、`check_page.py` 只报真问题（主按钮被挡、文字溢出、对比度、触控、写死的颜色、控制台报错），结论只有 `done` 或 `needs_work`；报根因，不报像素。审美和体验交给独立评审，两者不互相代替。
3. **验证者自己也要被验证**：改了检查规则，先跑 `design-bar` 的 `scripts/selftest.py`，在一块故意做坏的画板上确认每类问题都抓得到、好的状态不误报。观察者每周抽一次：故意坏的输入还抓不抓得到。
4. **有停止条件**：标杆原则都 ≥ 4 分且底线全过才算通过；一轮没有提升或已经 3 轮还没通过，就上报，不算通过（`docs/uiue/bar-sheet.md` §7）。
5. **一条意见代表一类问题**：同一类意见出现两次，必须沉淀进设计系统、`velicoach-content` 或检查阈值，并在 `docs/uiue/decisions.md` 或 `docs/requirements/trace.md` 记一笔。

## 4. 能做什么、不能做什么

照 Veli `observer.md` §7。

| 能做 | 要人确认 | 不能做 |
|---|---|---|
| 写观察报告；维护 `docs/quality/`；开票；**收紧**机制的 PR（加检查、加清单项、写清含糊的话、补技能例子）和白名单内的简化（合并重复条目、把含糊或过时的说法改清楚，不减要求），走冷评审后用合并脚本合并 | 删掉、跳过或放宽任何一项要求；改流程顺序、模型、频率；同步 Veli 的新版本号（`pipeline.md` §10）。写进「等你决定」并附推荐答案，或做成 PR 打 `owner:merge` | 写票里的代码或内容；评审或合并票的 PR；改权限设置；合并到 `site`；改本节和 §1 |
| **紧急刹车**：密钥泄漏、动了 `site`、集成分支红超过 4 小时、系统性伪造证据（包括编造出处），给状态 issue 打 `agent:stop` 并写明原因 | 解除 `agent:stop` | |

## 5. 什么时候跑、产出什么

| 节奏 | 做什么 | 产出 |
|---|---|---|
| 每天（日报之前） | 过去 24 小时的运行和合并：合规、抽查重跑、指标 | 状态 issue 一条「观察报告 <日期>」，10 行以内：结论、指标、最重要的 3 个发现和处理；详细版 `docs/quality/observer/<日期>.md` |
| 每周日 | 加做：需求覆盖、只读验证者自检、技能打磨（改进写进仓库的 `.grok/skills/`，账号里的副本落后就写明）、两个仓库的机制对比（`pipeline.md` §10）、规则账本、规范篇幅 | 每周机制评审：收紧的直接开 PR，放宽的进「等你决定」 |

阶段 1 每个合并的 PR 都抽查；之后 3 个抽 1 个。

**规范篇幅预算**：`docs/standards/*.md`、`docs/delivery/loops/*.md`、`.claude/agents/*.md`、`AGENTS.project.md` 合计不超过 6 万字节（`quality-terms.md` 是词典，和术语表一样不计入），量法 `ls docs/standards/*.md docs/delivery/loops/*.md .claude/agents/*.md AGENTS.project.md | grep -v quality-terms | xargs cat | LC_ALL=C wc -c`。超了先合并或删掉同样多的内容，再加新的。主站的机制靠引用 Veli 的版本，不复制原文，所以预算比 Veli 小。
